# 16. 长期驻守、重启恢复与需求 intake

- 状态：2026-11-17 需求草案 + v0 intake；完整长期运行机制未实现。
- 关联：[00 合同 §16.2](00-requirements-contract.md) · [13 MVP 架构](13-mvp-architecture.md) · [14 角色与计划](14-role-templates-and-roadmap.md) · [记录 19](records/2026-11-17-19-long-running-intake.md)

## 1. 为什么

用户的目标不是“跑一次漂亮的 demo”，而是：

- 多个 agent **长期驻守**，像一人公司的常驻团队；
- 电脑/服务重启后能恢复 agent、房间、上下文和未完成工作；
- 独立的、稳定的业务流可以持续运行（定时/触发/长任务）；
- 单个任务不一定需要团队；先评估问题，再决定“单点解决”还是“小团队运营”。

一次性小任务（例如改一个小 bug）用整个团队通常不划算；benchmark 已看到 6 人队成本约 22×。

## 2. 需求

### Must（草案）

1. **驻留与恢复**
   - app / gateway / 宿主机重启后，agent 身份、房间、成员、状态、成本记录恢复；
   - 不重复回复已消费消息；
   - 未完成的长任务不丢：至少能恢复“待办/进行中/已完成”，而不是只丢在内存里；
   - agent 的 session/memory 恢复（已有 `sessionScope:"agent"` 的本地 session store）；
   - 重启期间的消息在恢复后按顺序处理一次。
2. **长期任务**
   - 任务台账：task id、owner、状态、截止/下一次运行、检查点、产物；
   - 暂停/恢复/取消；失败重试与人类升级；
   - 预算（每日/每任务）与超预算告警；
   - 定时/触发（cron/事件/人类指令）。
3. **Intake 评估**
   - 人类提交问题后，评估 agent 先重述目标、约束、验收标准；
   - 给出选项：单点 agent / 2–3 人小队 / 更大团队；
   - 明确推荐及理由、角色分工、成本/风险、最小验证、下一步；
   - **默认优先单点**，只有独立性/风险/并行收益足够时才推荐团队；
   - 人类批准后才创建团队/长期任务，不自动扩张。
4. **可观测**
   - 每个 agent/任务的审计、成本、当前状态；重启后仍然可查。

### Should

- 一键把 intake 推荐转成“单 agent 房间”或“团队 + 群 + 任务”；
- 常驻团队的“值班/待命”状态，不被每条消息唤醒；
- 定时摘要/日报；
- 任务失败/预算超限通知（IM 内提醒）。

### 非目标（v0）

- 真正的 7×24 高可用/多机容灾；
- 容器/VM 级强隔离；
- 自动无人审批地创建团队、发外部消息；
- 完整 BPM/工作流引擎。

## 3. Intake 流程

```text
人类问题
  → intake agent（默认 facilitator/需求顾问）
  → 输出：
      1. 重述：目标 / 约束 / 验收
      2. 选项：single | pair | squad
      3. 推荐 + 理由
      4. 角色（如团队）
      5. 成本/风险/最小验证
      6. 下一步
  → 人类选择：
      A. 单 agent 解决
      B. 按推荐创建小队
      C. 先做最小验证
      D. 取消
```

推荐规则（写进 prompt）：

- 单点能闭环 → 推荐 single；
- 需要独立验证/不同专业/并行才考虑 pair/squad；
- 明确说“团队多花多少、换来什么”，不为了热闹组队；
- 不确定时先给最小验证，不直接建大团队。

v0 已实现：`POST /api/intake` 确保一个 `@intake` 需求顾问、打开/复用 DM、发送评估 prompt；建议以聊天消息返回，人类自己决定是否创建。

## 4. 重启恢复的现状与差距

已有：

- `app/data/state.json` 保存 human/agents/rooms；重启恢复；
- `gateway-state.json` 保存 sync since/processed；重启去重；
- operator 启动脚本可重新拉起 app/Tuwunel；agent session 存在本地；
- 已多次重启验证不重复回复。

差距：

- 进行中的 turn 崩溃会丢该轮回复（设计选择：不重跑，避免重复）；
- 没有持久 task ledger / 检查点；
- 没有定时器/触发/长任务恢复；
- 没有进程守护/自动重启（可后续用 Windows 任务计划或 WSL systemd）；
- 预算/暂停是内存 + state 部分，重启后预算花费从 audit 恢复，但任务状态没有。

## 5. 验收草案

1. 重启 app 后：所有 agent 出现在 Agents、房间和未读恢复、session 继续、不重复回复。
2. 一个 10 分钟长任务在 app 重启后能显示“进行中/待恢复”，而不是无声丢失；人类可选择恢复/放弃。
3. 定时任务在重启后按 nextRunAt 补跑/跳过，不重复执行。
4. 人类提出问题 → intake 在合理时间返回“单点/小队”建议，包含成本/风险；不自动创建团队。
5. 超预算/连续失败 → 暂停并通知人类。

## 6. 待定

- 任务台账存 state.json、独立 JSONL 还是 SQLite？
- 重启时“进行中的 turn”是恢复、重跑还是标记失败？（当前倾向：标记失败，人类决定）
- 定时任务用进程内 timer 还是外部 cron/任务计划？
- intake 的推荐是否要结构化标签（`RECOMMEND: single|pair|squad`）供 UI 解析，还是先自由文本？
- 一人公司场景是否需要“人类不在线时的自治上限”（预算/审批/白名单）。
